# Reorder batch-rename targets — 2026-10-30

Independent adaptation of [Double Commander’s reorderable Multi-Rename file list](https://doublecmd.github.io/doc/en/multirename.html#interface), cohort repository #3. Commander exposes adjacent Up/Down buttons in its existing virtualized preview; arbitrary permutations are possible through successive moves. This milestone does not add the source tool’s drag/drop or Shift-arrow interactions. No upstream code copied.

For batches with multiple targets, each preview row now has Up/Down controls. Boundary actions disable. Moves change only the captured target order, retaining directory/panel scope, target membership, directory-kind and existing-sibling sets. Counter assignment follows that order. The rule/preset contains no target names or file order: opening another batch captures its own listing order, while loading/resetting rules within the current batch does not replace its target order.

Mutation is deferred until after preview rendering. A successful move invalidates the cached validation even when the rule itself is unchanged, clears the stale error and requests repaint. Submission is suppressed in that control frame, so an old ordinal-to-name map cannot be applied together with the move. The next preview and eventual application use the reordered context. Invalid/no-op moves preserve the cached plan and error. Preview row height increased to 24 points for the small controls; remaining width still truncates long names instead of widening the sheet.

A regression changes photo.txt/notes.md/folder order under Counter only, verifies rebuilt 01.md/02.txt/03 mappings, submitted rule, membership/kind retention, restoration and invalid/no-op cases. A real workspace test applies a two-file reordered counter map, verifies the correct file payloads at 01.md and 02.txt, and exercises Undo/Redo. Existing staging/collision guards remain unchanged.

It scrolls to the preview, clicks Down on row zero, requires notes.md→01.md and TXT-TXT.txt→02.txt, then clicks Up on row one and requires the restored ordinal mapping at final phase 82. This seeds the multi-file fixture programmatically; reordering itself uses actual UI events. No rename is submitted by the native scenario.
