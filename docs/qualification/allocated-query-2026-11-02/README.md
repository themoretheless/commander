# Allocated-size search predicates

Independent adaptation of [Dust minimum-size filtering and apparent/disk-size distinction](https://github.com/bootandy/dust/blob/master/README.md), cohort #82. No upstream implementation copied.

Find accepts `allocated:>1MB`, `allocated:=0`, inclusive ranges and the existing size operators/units, independently of logical `size:`. Repeated conditions combine through AND and survive expression/saved-query serialization. `allocated:=0 size:>1MB` finds a logically large sparse file with known zero allocation. Metadata matching uses retained observations; there are no extra stat or content reads for this filter. Explanations include the observed allocated byte count and search JSON gains a nullable allocated_bytes field.

Native Unix regular files use already fetched blocks times 512 with checked arithmetic. New indexes persist optional allocated_bytes with sufficient serialized-size budget and restore it only for consistent regular, non-link, non-directory records. Old indexes remain readable but their absent allocations are unknown; rebuild to populate them. Cached allocation remains an observation after deletion. Known non-regular kinds never qualify and are not counted as unknown coverage. Unknown allocations on potentially regular files count as skipped, including archived regular payloads and old/non-Unix records. ZIP compressed/decompressed sizes are never substituted for filesystem allocation.

## Validation

Three regressions cover grammar/mode/query round trips, strict/range/overflow errors; real sparse/dense/empty files and excluded links/folders across live and JSON-round-tripped index providers in all matching modes; size/content conjunctions, old snapshots, retained facts after removal and contradictory cached classifications; and search JSON zero/full-width/unknown values. Existing worst-case document-size coverage includes the new cache field.

Native allocation_search enters three real Find queries and compares rows and explanations with separately captured filesystem block counts. Empty and sparse files qualify at zero; dense files qualify above zero; the logical-size conjunction retains only the 8-MiB sparse file. One archived regular payload has unknown allocation and remains explicitly skipped. Native search_json reruns full/selected/hidden/draft/empty report workflows with the additive allocation field. See checks.json, validators.json, tests.log, verification.log and native-captures for final evidence.

Allocation is not exclusive or reclaimable storage: hard links, shared blocks, snapshots and filesystem policy can change that relationship. Windows allocation and per-archive-member disk accounting are not established. Counts are listing/index observations, not a live storage certificate or authorization for deletion.

Early neighboring search_json attempts stopped progressing at different scripted interactions and eventually timed out; an inspected sample showed the main thread in the native event/render path rather than a Rust mutex wait. The QA hook requests delayed frames, and the two allocation/report scenarios now additionally request continuous repaint from ui; JSON input events are spaced at least 60 ms apart. Both final-source captures then completed with unchanged pass conditions. These changes are confined to visual QA. Earlier attempts and launch records are retained.

Final validation: all six checks passed; **3140 tests passed, 3 ignored**. Both native scenarios passed **16/16**, on the same final binary: allocation_search recorded zero external effects; search_json recorded exactly five intercepted clipboard writes. Both final frame images were inspected. The independent verifier compares allocation query results against raw filesystem block counts, checks all five JSON report variants, and binds source, binary and oracle hashes. This qualifies the observed macOS/Unix behavior; it does not establish Windows allocation support or complete parity with the 99-repository cohort.
