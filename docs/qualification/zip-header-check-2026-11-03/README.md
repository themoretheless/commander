# Opt-in strict ZIP header validation

A continuation of cohort #96 PeaZip-inspired archive integrity work. [PeaZip's corruption guidance](https://peazip.github.io/peazip-password.html) distinguishes damaged headers from readable payloads and discusses the consequences of permissive error handling. The specific Strict ZIP headers option is Commander's integration of the existing zip-rs 9.0.5 validation API, not a claim that PeaZip exposes an identical toggle.

The archive pane adds a runtime-only, initially off Strict ZIP headers checkbox beside Test archive. It is disabled while archive operations run and resets when the pane is reopened. A successful report records the mode and shows a strict ZIP headers suffix. The worker retains ephemeral/empty/UTF-8-password handling and zeroizes its owned password before publishing its result. TAR checks remain ordinary TAR checks and never claim ZIP header validation.

Strict mode validates local/central header identity and data metadata through zip-rs before decoding members. It additionally rejects duplicate central-directory names and overlapping entries. Existing member/decoded-byte limits, cancellable ZIP reads, source identity/change checks, CRC/size/AES validation and read-only behavior remain. Ordinary mode stays available for compatibility: valid ZIPs can contain duplicate names, and permissive readers can use their central-directory view. Strict rejection of such ambiguity is a mode policy, not a claim that every rejected archive has corrupt payload bytes. This is not a full forensic ZIP certification or an extraction-path/permission certificate; reserved fields and every extra-field type are not independently audited by Commander. Extraction retains its own confinement checks.

make_fixtures.py generates deterministic Python ZIP fixtures. Eight mutations keep the central directory and payload intact while changing only the local name, compression method, encryption/descriptor flags, timestamp, CRC, packed size or decoded size. Rust regressions demonstrate ordinary payload success and strict rejection before decoded-byte progress. A duplicate-name control remains readable in compatibility mode but is refused in strict mode. Valid encrypted ZIPs and actual descriptor entries are accepted; worker propagation, cancellation and a decoded limit are covered. These are three new Rust regressions.

Official 7-Zip 26.05 results are retained verbatim in oracle.json. Its behavior is not identical to the selected strict policy: it accepts the local-name mismatch and valid duplicate-name archive, rejects other mutations with its recorded codes, and exits 255 on the local encryption-flag mismatch without a supplied password. No claim of universal external rejection is made. The structural mutation and independent source payload/CRC provide the oracle for the stricter identity policy. No external decoder runs in the application and no dependency versions changed.

It retains extraction/repeat and wrong-password checking, clicks the real Strict ZIP headers checkbox, enters the correct Unicode password and clicks Test archive. Read-only observations require strict_headers=true, an explicit successful strict summary, exact counts, an empty password field and unchanged extracted bytes.
