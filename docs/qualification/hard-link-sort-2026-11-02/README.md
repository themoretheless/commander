# Hard-link count listing and ordering — 2026-11-02

Independent adaptation of [eza hard-link count presentation (-H/--links)](https://github.com/eza-community/eza/blob/main/man/eza.1.md), cohort #79, extended with Commander-specific numeric ordering. Eza's documented sort-field list does not include link count; this is not a claim of identical upstream sorting behavior. No upstream source copied.

Sort by hard-link count selects the Links metadata column in list view and adds a Hard links line in icon view. Activating it again reverses the numeric ordering. Existing folder grouping, name ties, cursor, visible/hidden selections, folder tabs and saved ViewConfig remain owned by their existing code. Metadata comes exclusively from captured listing observations; sorting/rendering do not stat files. Counts include names outside the current folder. Symbolic links/directories expose no regular-file count, and missing counts stay unknown/last in both directions after the existing folder grouping. Numeric zero is a known value and full u64 counts remain exact. Counts do not imply reclaimable space.

Tests cover numeric zero/MAX, natural name ties, unknown-last in both directions, folder-first interaction, serde persistence and retained observations/cursor/selection after source removal. Native hard_links_sort uses six command-palette sorts (ascending/descending link counts, names, then link counts again), with a captured hard-link pair whose third alias is outside the root, a distinct regular file, a symbolic link and a directory. A hidden selected file and cursor must survive all six states. Raw Unix nlink/device/inode/type observations are compared independently against order and listing JSON. Neighboring inode_sort runs on the final binary. Logs, source/binary hashes, reports and native screenshots are retained.
