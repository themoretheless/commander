# Duplicate groups with the same root-relative path

Independently adapts [rmlint --match-relative-path and ASCII case matching](https://github.com/sahib/rmlint/blob/master/docs/rmlint.1.rst), cohort #86. No upstream implementation copied.

Duplicate files → Name filters → Group by → Same relative path compares every path component below each captured scan root, including the filename. Optional Ignore ASCII grouping case folds only these relative keys; root ownership itself remains literal. Apply/Reset retain the existing draft/applied and manual-choice lifecycle. The existing JSON names context records RelativePath and its applied case policy.

The most specific captured root owns each path, consistently with cross-root membership and result labels. No canonicalization, symlink resolution, guessed parent or live-panel retargeting is added. Root-relative empty paths, parent traversal and paths outside all captured roots cannot match. The worker counts missing/invalid ownership as scan issues before hashing. A single root normally has unique relative keys; finding no duplicate group in that scope is expected. Including another root allows, for example, docs/report.txt to match docs/report.txt in another tree, while misc/report.txt remains distinct.

Current-listing scans now receive their explicit opening root independently from the fresh-enumeration flag. They still hash only captured eligible rows, without enumerating newly added children. Tree/two-root scans retain fresh enumeration. Full content digest confirmation remains prerequisite; minimum-copy, extension constraints and cross-root membership are reapplied. Existing physical-file identity collapse and Trash validation remain unchanged. The eligible representative of a hard-linked object is still the only alias used for grouping. This does not implement directory merging or all rmlint hard-link policies.

## Validation

Two pure regressions cover exact/ASCII keys, longest-root ownership independent of root order, component boundaries, parent traversal, missing roots, thresholds, cancellation, Unicode and non-UTF-8 keys without lossy labels. A real-worker regression uses four/overlapping roots, content-different same-size files, minimum-copy/cross-root rules, captured-listing non-enumeration, visible ownership errors and hard-link representative selection. Seven focused relative-path-related tests passed before final qualification.

The native workflow uses two trees, stages/applies exact and ASCII-relative matching, toggles cross-root-only, resets, disables the second root, verifies an empty single-root relative result, then resets/restores the second root. It preserves every transition, its JSON plan and seven original source files. Independent Python/hashlib checks compare relative keys, memberships, keep actions and counts/bytes. Neighboring duplicate_roots must retain original opening folders while displayed panes navigate away. Windows rendering and arbitrary byte filenames on APFS remain unqualified; pure byte-path regressions need no filesystem I/O.

The empty single-root state intentionally has no JSON report: Duplicate Finder's existing report contract rejects empty records, and the native snapshot records null rather than fabricating an export. Verification checks that exact empty transition separately; all twelve nonempty transition reports remain required. The verifier's original assumption that every state exported a JSON document was corrected against the existing report guard and its regression, without changing product behavior.

Final qualification: all six commands passed; **3167 tests passed, 3 ignored**. Native `duplicate_relative` and neighboring `duplicate_roots` each passed **14/14** on the final binary. Relative grouping recorded zero external effects; the neighboring roots workflow recorded exactly one intercepted JSON clipboard write, all other effects zero. Independent SHA-256/relative-key verification passed all thirteen transitions, twelve nonempty JSON proposals and the explicitly unexportable empty state, with final source/binary/tool hashes bound. Both final screenshots were inspected.

The native workflow exposed an 8.5-pixel panel overflow caused by the result area's minimum height. The first containment correction left too little visible result space because the old fixed 96-pixel footer reserve was excessive. The final implementation removes egui's implicit 64-pixel minimum and computes the reserve from current button/text/spacing metrics. Acceptance now additionally requires at least 40 logical pixels of visible result viewport, inside the window; the final measured viewport is **55.5 pixels** high. Earlier stages and captures remain under `before-height-fix`, `before-footer-budget-fix` and `native-captures`; acceptance uses only the final source/binary. The ordinary non-QA check retains the existing unrelated unused `response` warning in `src/diff_find.rs:136`; visual-QA all-target Clippy with warnings denied passed.
